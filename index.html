What it is

Vega ships a canvas renderer and an svg renderer. This is a third one, built on WebGPU. It registers itself with Vega's renderer module, so nothing about a spec changes: the same scenegraph is drawn with GPU pipelines instead of 2D canvas calls.

The canvas renderer is the reference. Every spec in the corpus is rendered both ways and compared pixel by pixel on every commit, so a difference is a tracked defect rather than a surprise. The render gallery shows every case as each of the last ten runs on main and every release drew it, and what is still off is listed under features and roadmap.

Needs a browser with WebGPU. Without one, 'webgpu' draws with the canvas renderer, see falling back.

Use it

Script tag

The renderer registers itself when loaded after Vega.

<script src="https://cdn.jsdelivr.net/npm/vega@6/build/vega.min.js"></script>
<script src="https://kanadaat.github.io/vega-webgpu/releases/2_0_0-rc5/vega-webgpu-renderer.js"></script>
<div id="vis"></div>
<script>
  fetch('https://vega.github.io/vega/examples/bar-chart.vg.json')
    .then(res => res.json())
    .then(spec => {
      new vega.View(vega.parse(spec), {
        renderer: 'webgpu',
        container: '#vis',
        hover: true,
      }).runAsync();
    });
</script>

Every hosted build is listed under versions, each with its own page.

Match the Vega major version. 2.0.0 and later target Vega 6. Everything before it targets Vega 5 and throws Class constructor cannot be invoked without 'new' when loaded next to Vega 6, because a renderer registers itself against whichever Vega is already on the page.

Falling back

Without navigator.gpu, 'webgpu' draws with the canvas renderer and warns. A browser can also have navigator.gpu and no adapter, a blocklisted GPU for instance, and then nothing is drawn. To fall back there too, pick the renderer from the adapter: 

const renderer = (await navigator.gpu?.requestAdapter()) ? 'webgpu' : 'canvas';
new vega.View(vega.parse(spec), { renderer, container: '#vis' }).runAsync();

Config

Options live on view._renderer.wgOptions and can be changed between frames.

const view = new vega.View(vega.parse(spec), { renderer: 'webgpu', container: '#vis' });
view._renderer.wgOptions.debugLog = true;
Option What it does Default Since
sampleCount MSAA samples per pixel: 4 for antialiased, 1 for plain. Anything else falls back to 4. Pipelines rebuild on the next render. 4 2.0.0
redrawOnZoom Follow browser zoom. Zoom changes devicePixelRatio, and the default resizes the canvas and redraws so the view stays sharp. When false the canvas keeps the ratio it was first sized at and the browser scales it, which is softer but skips the redraw and cannot grow past the texture cap. true 2.0.0
renderLock Skip re-entrant render calls while a frame is in flight. The most recent request always runs, so an interactive chart stays responsive under a drag. true 1.1.1
cacheShapes Keep triangulated shape geometry between frames instead of rebuilding it. Costs memory on a scene whose geometry changes every frame. true 1.1.0
debugLog Log per-frame render timings to the console. false 1.0.0
offscreen Render into a texture the renderer owns and never touch the canvas swapchain. For a headless runner with no compositor, where acquiring the swapchain destroys the device. The canvas stays blank, so the frame is only reachable through captureFrame(). false 2.0.0
canvasTextDrift Place each label where the canvas renderer would, which can be a row off on a half pixel baseline. Only for matching a canvas view side by side. false 2.0.0

renderBatch and simpleLine were removed in 2.0.0. The line mark batches its segments unconditionally now, so neither had anything left to switch.

Feature completeness

All twelve of Vega's mark types are drawn: arc, area, group, image, line, path, rect, rule, shape, symbol, text and trail. Fill, stroke, opacity, clipping, corner radii, symbol shapes and rotation, and text layout all work on every mark that has them. The table is the properties that used to stop at some marks, and each now reaches every mark that has it.

Mark

Every mark name is a link into the playground, where you can tick these properties on and off and watch canvas and WebGPU draw the same spec side by side.

Known differences from canvas

  • No seam between abutting fills. Two polygons sharing an edge, a choropleth's counties for instance, come out with no line between them. Canvas fills each polygon separately so about a quarter of the background survives on the shared edge, which is the seam you are used to seeing. One multisampled pass covers that edge completely. Ask for the border with a stroke instead, which is clearer about the intent and matches everywhere. Reproducing the seam is planned for a release after 2.0.0.
  • Edges of triangulated marks. arc, area, path and shape take their edge coverage from MSAA, which expresses quarter steps, so an edge landing on a pixel boundary can read a quarter light or heavy against canvas. rect, rule, symbol and line segments compute coverage analytically and do not have this.
  • Maximum canvas size. The canvas is a GPU texture, so its device pixels are capped at the adapter's maxTextureDimension2D, usually 16384 on a desktop GPU and never less than 8192. A view past that draws at a lower pixel ratio that fits, softer than asked for, with one warning. Keep width and height times devicePixelRatio under the cap for full sharpness.
  • An erasing operator inside a clip path. source-in, destination-in, source-out, destination-atop and copy clear what lies outside the source, and inside a clip path they clear the path's whole bounding box where canvas clears only the path. Queued for 2.1.0.

Roadmap

Broad strokes. The full list, with the measurement behind each item, is in ToDo.md.

Next

2.0.0 is out. What is left is getting it into Vega.

  • Report the bugs found in the canvas renderer along the way to Vega
  • Propose it to Vega as an official renderer

2.1.0 and later

Worth doing, not worth holding a release for.

  • Analytic edge coverage for triangulated fills, so an edge on a pixel boundary matches canvas rather than landing a quarter step off
  • Publish to npm
  • Viewport clipping, so a very tall view draws only what is on screen
  • Tiled rendering for a canvas past the GPU's texture cap
  • Per-item compositing, which is what would reproduce canvas's polygon seams
  • Performance: feed d3-geo a path sink, reuse buffers, cache bind groups

Set up locally

git clone https://github.com/KaNaDaAT/vega-webgpu.git
cd vega-webgpu
npm install
npm run build     # UMD, minified and ESM bundles plus type declarations, into build/
npm run serve     # serve the repo at http://localhost:5500

Then open http://localhost:5500/test/?spec=bar&renderer=webgpu&version=dev to run the local build against any spec in test/specs-valid. The page can show canvas and WebGPU side by side and a pixel diff between them.

Command What it does
npm run dev Rollup in watch mode
npm test Render every spec both ways and compare, from the build
npm run test:report Open the last run's HTML report
npm run gallery:record Record every case to test/render/output
npm run gallery Browse the recorded cases, or render them live
npm run typecheck Strict TypeScript, no emit
npm run lint eslint
